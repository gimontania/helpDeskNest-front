| 17-nov | US-01-Login | #1 | Inicio de sesión con persistencia en el frontend. Formulario con react-hook-form y zod: si el correo o la contraseña son inválidos no se envía ninguna petición. Las credenciales válidas llaman a POST /auth/login, guardan el token y abren la vista autorizada según el rol. Un 401 muestra un mensaje genérico, sin indicar si falló el correo o la contraseña. La sesión se restaura al recargar leyendo y validando el JWT (rol, correo y expiración). Si el token es inválido o está vencido, se borra. Cerrar sesión limpia el store y el token. api.ts adjunta Authorization: Bearer a cada petición. Un 401 con sesión activa cierra la sesión automáticamente |
| 18-nov | US-05-CRUD_Categorias | #5 | Crear y editar categorías para ADMIN y AGENTE. Esquemas Zod según el contrato de la API: si el nombre está vacío o supera 100 caracteres no se envía ninguna petición. Formulario reutilizable para alta y edición: al editar se precargan los datos de la categoría. Las mutaciones llaman a POST /categorias y PATCH /categorias/:id y, si salen bien, muestran un aviso y vuelven a pedir el listado. Si la API rechaza la operación, el formulario conserva lo escrito: un 409 marca el campo nombre como duplicado y un 403 informa falta de permisos. El listado muestra estados de carga, error con reintento y vacío |
| 19-nov | US-08_BandejaGlobal | #X | Bandeja de tickets según el rol. El EMPLEADO ve sus propios tickets como “Mis tickets” y ADMIN y AGENTE ven la bandeja global, con la autorización aplicada por GET /tareas en la API. Se ampliaron los esquemas Zod del ticket con categoría, creador y fecha. Se crearon badges compartidos de estado y prioridad. El listado es responsivo en tarjetas. Como la API no acepta parámetros de consulta, los filtros por estado y categoría se aplican en el cliente, con botón para limpiarlos y contador de resultados.
